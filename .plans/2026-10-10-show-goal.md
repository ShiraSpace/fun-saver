## The menu-morph warning, resolved

`e2e/menu-morph.visual.ts` seeds one account and **no goal**. In this PR
`MenuGoal` renders nothing without a goal, so the suite is unaffected as it
stands. With a goal it would break: estimated from the styles, the one-account
list reaches ~49 px past the per-account block's top, and the goal row (42 px
thumb + padding + margin) adds ~77 px between them.

Keep the mockup's place (under `AccountPicker`, above the edit link) and make
the suite measure the tallest controls this PR can draw: seed it with
`goals: [mockGoal]` and a second account (`mockSiblingAccount`). The extra list

trusted from this estimate; a third account if it falls short. PR 4 adds
«ביטול היעד» under the row and must re-measure (note added to the parent plan).

## Step 1 — How far a goal is (`src/lib/goal`)

### Production

**`src/lib/goal/saved-toward-goal.ts`** (name proposed, see Names)

```ts
export interface SavedTowardGoal {
  goal: Goal;
  saved: number;        // agorot, floored to whole shekels
  stillToSave: number;  // agorot: goal.amount − saved, never below 0
  reached: boolean;     // goalReached(goal, savings balance)
}
export function savedTowardGoalOf(account: AccountSummary): SavedTowardGoal | undefined
```

`undefined` when `account.goal` is. Savings via `walletNamed(…, WALLET_NAMES.savings)`.
`saved` is floored so every screen shows the same number and the bar is full
exactly when `reached` (goal amounts are whole shekels). `stillToSave` is taken
from the floored `saved`, so ₪299.50 of ₪300 reads "עוד ₪1", not "עוד ₪0".

Commit: `feat(goal): how much is saved toward a goal, as every screen shows it`.

### Tests — `src/lib/goal/__tests__/saved-toward-goal.test.ts`

1. *an account without a goal has nothing saved toward one* → `undefined`.
   Break: return a zero object.
2. *what is saved is floored to whole shekels* (balance 29950 → 29900). Break:
   `saved = balance`.
3. *what is still to save counts from the floored amount* (29950 of 30000 → 100).
   Break: `goal.amount − balance`.
4. *the goal is reached once savings hold its amount* (30000 → true). Break: `>`.
5. *what is still to save never goes below zero* (40000 → 0). Break: drop the `max`.

## Step 6 — A `409` refreshes the drawer

### Production

**`use-amount-entry.ts`** — in the `catch`: a `RequestFailedError` with
`StatusCodes.CONFLICT` → `router.refresh()`, then `failed` like any other
error. The drawer stays open; the refreshed account draws the lock, which hides
the error. If the refresh finds no lock (another phone completed the goal), the
error stays, so the child knows the withdrawal did not happen.

Commit: `feat(goal): a withdrawal refused for a goal refreshes into the lock`.

## Decided (2026-10-10)

1. **One number everywhere.** While a goal is active, every place that shows
   the savings balance beside the goal floors it the way the goal line does:
   the savings `WalletCard` (step 4, `rounding` passed to its `Money`) and the
   savings tile in the drawer (step 5). The donut's legend sits away from the
   goal and keeps rounding to the nearest shekel. Tests: *a card with an active
   goal floors its balance* (break: keep `nearestShekel`) and the same for the tile.
2. «עוד ₪…» counts from the floored saved amount (₪1 left, not ₪0), as planned.
3. **The 409 gets a browser test** (step 7): `e2e/goal.e2e.ts`, seeded with
   `mockAccount` and `mockTransactions` and no goal. (The JSON store reads
   the file on every request, so the server sees the goal.) The test opens the drawer, picks savings
   and types an amount, then a driver method writes a goal into the store file
   (`server.storePath`, the same atomic write `writeInitialStore` uses), then
   submits. Expected: the drawer refreshes into the lock panel and shows no
   error alert. Break: drop the `CONFLICT` branch in `useAmountEntry`, so the
   alert shows and the test reddens.
